ML Capstone Platform

Capstone reference architecture

For students: download the raw file and put it in your repo at docs/reference-architecture.md. Add one line to your CLAUDE.md or AGENTS.md:

Follow docs/reference-architecture.md for structure, layering and naming. When the code and that file disagree, ask before changing either.

Then ask your agent things like "add a feature that saves a user's favorite items", and it will put each piece in the right place. When you set the project up, also ask it to do the "Draw your map" task at the end. That gives you a diagram of your own architecture.

For the coding agent: everything below is a rule for this repository unless the project's own CLAUDE.md or AGENTS.md says otherwise. If a rule blocks what the user asked for, say so and propose the smallest exception. Don't quietly break it.

1. The shape

Requests flow one way, top to bottom, and never back up:

browser → frontend → backend → { database, model service, hosted model APIs }
ContainerFolderPublic?Job
frontendfrontend/yes, the only oneThe UI. It forwards /api to the backend and holds no secrets.
backendbackend/noAll rules and all data access. The only container with the database password or model API keys.
dbnone (Postgres image)noPostgres. The schema lives in backend/migrations/.
model servicemodel-service/noOptional. Your own model, when it needs a GPU or a different language.
hosted model APIsnoneoutsideOptional. OpenAI, Claude, etc., called only from the backend.

Add a container only when a part needs different hardware, a different language, or its own scaling. Most projects need three: frontend, backend, db.

The platform's deployment rules (one public service with expose:, health checks, named volumes, restart:) are in Migrating Your Project, requirements R1–R9. This file covers what goes inside each container; that one covers how the containers are deployed. Follow both.

2. Directory layout

Keep this layout. Each folder has one job, so a change touches one folder.

your-project/
├── CLAUDE.md, AGENTS.md          the rules (this file is linked from them)
├── README.md
├── docker-compose.yaml           every container; `expose:`, not `ports:`, in production
├── docker-compose.override.yml   local-only changes (ports, fake engines)
├── .env.example                  every setting, with a safe default or a comment
├── smoke-test.sh                 builds, starts and checks the whole stack

│       └── components/           pieces shared by pages
├── backend/

│   ├── requirements.txt

│   ├── engines/                  real.py and fake.py behind one interface
│   └── tests/
└── terraform/                    deploy wiring, if your course uses it

If you started from hello-world-app, its frontend is a small Python app. Then frontend/backend_client.py plays the role of src/api/client.ts. Its backend begins as main.py plus notes_dao.py; move to the layout above once the backend has more than one or two tables.

3. Backend layers

LayerFolderMay callMust never
controllersapp/controllers/one service method per routecontain SQL, rules, or model calls
servicesapp/services/DAOs, engines, ml/, clients, other servicesimport FastAPI or return HTTP codes
enginesapp/engines/ml/, other enginestouch the web or the database
model seamapp/ml/base.py, app/ml/router.pyproviderscall a model itself: it only picks one
DAOsapp/dao/the databasecontain rules
clientsapp/clients/one other container or APIcontain rules
model providersapp/ml/providers/one model SDK or endpointcontain rules, or be skipped: nobody else imports a model SDK

Engines and adapters are peers, not a stack. A service calls an engine when it needs a decision and an adapter when it needs the outside world, and neither one calls the other. The single exception is the seam: an engine may ask the router for a model, and the router reaches a provider. The drawings put the adapters below the engines so each one sits directly above the container it reaches, which is a layout choice, not a claim that engines depend on them.

The last three rows are adapters: the only code that reaches anything outside the backend. app/ml/ straddles that line, which is why it appears twice. router.py reads config/models.yaml and picks a provider for the role it was asked for; it makes no network call, so it sits with the engines as plain Python. The call happens one level down, in app/ml/providers/, which is an adapter like the DAOs and the clients. That split is the point: an engine can ask for a model without anything in the engine knowing a model exists.

Rules:

  1. Controllers are thin. Parse the request, call one service method, return the result.
  2. Services hold the rules and raise errors, not HTTP codes. They raise the classes in services/errors.py. One handler in main.py turns each into an HTTP code (NotFound → 404, Forbidden → 403, Conflict → 409, Invalid → 422, Unavailable → 503).
  3. All SQL lives in app/dao/. DAOs return plain dicts or models.
  4. A service runs the whole job. It holds the order of steps: load state, call an engine when it needs a decision, call a client when it needs the outside world, write the result through a DAO. A service may call another service for a step it already owns. Nothing below a service calls back up into one.
  5. Engines are plain code. They take data in and return data out, so they are easy to test. An engine never calls a DAO or a client: a service does that and passes the result in. The one thing an engine may reach for is ml/, and even that only picks a model rather than calling one.
  6. Only app/ml/ knows which model runs. Code asks for a role ("classifier", "summarizer"); config/models.yaml maps the role to a provider and model, with a fallback. The router picks; the provider calls. Adding a model means one new file in providers/ and one line in the router.
  7. Every model has a fake. providers/fake.py returns canned answers, so tests and laptops never need a GPU or an API key. Select it with an env var (ML_FORCE_PROVIDER=fake).
  8. Every call that leaves the backend goes through one file: app/clients/ for another container, app/ml/providers/ for a model. That file turns network errors into one error type.

A service is where these rules become visible, because it is the only place that knows both bands exist. Every other line reaches sideways to one helper or the other:

# backend/app/services/document_service.py
async def submit(self, user, document_id, text):
    doc = await self.documents.get(document_id)          # adapter
    if doc is None:
        raise NotFound("no such document")               # a rule, not a 404
    if doc["owner_id"] != user["id"]:
        raise Forbidden("not yours")

    cleaned = normalise(text)                            # engine
    if not cleaned:
        raise Invalid("write something first")

    summary = await self.summariser.run(cleaned)         # engine, which asks ml/
    await self.search.index(document_id, summary)        # adapter
    return await self.documents.save(document_id, summary)   # adapter

Read the right-hand column: adapter, engine, engine, adapter, adapter. The service alternates. normalise() cannot read the database and self.documents cannot decide anything, so neither can be pulled into the other's job. The one call that goes deeper rather than sideways is self.summariser.run(): an engine asking the seam for a model.

The same feature written wrongly, for contrast. It still passes its tests, and it is the shape to refuse:

# WRONG: the engine fetches its own data and calls its own model
class Summariser:
    def __init__(self, documents: DocumentsDAO, openai_client):
        self.documents = documents        # an engine owning a DAO
        self.openai = openai_client       # an engine owning an SDK

    async def run(self, document_id):
        doc = await self.documents.get(document_id)        # SQL from an engine
        return await self.openai.responses.create(...)     # the web from an engine

Now the engine needs a database and an API key to test, the service no longer holds the order of the steps, and swapping the model means editing logic. Keep the fetch in the service, pass data in, and let ml/ name the model.

Checks that should print nothing (a match inside a comment or docstring is fine):

grep -rnE "SELECT|INSERT|UPDATE|DELETE" backend/app --include=*.py | grep -v "app/dao/"
grep -rn "fastapi" backend/app/services backend/app/engines
grep -rnE "import (openai|anthropic|torch|transformers)" backend/app | grep -v "app/ml/"
grep -rnE "^(from|import) app\.(dao|clients)" backend/app/engines

4. Wiring: one place builds everything

  • app/container.py has build_container(settings). It creates every DAO, client and service once, passes each one what it needs, and returns a Container object. No class creates its own helpers.
  • main.py has create_app(settings=None, container=None). It:
    1. calls build_container(), unless a container was passed in;
    2. keeps it on app.state.container;
    3. registers each controller module's router;
    4. maps service errors to HTTP codes;
    5. on startup, opens the database and applies migrations.
  • controllers/deps.py has container(request), which returns request.app.state.container. Routes take it with c: Container = Depends(container) and call c.<service>.<method>(…).
  • A new DAO or service gets wired in container.py and nowhere else.
# backend/main.py (shape)
def create_app(settings=None, container=None) -> FastAPI:
    settings = settings or Settings.from_env()
    app = FastAPI(lifespan=lifespan)                       # lifespan: db.open(), migrations
    app.state.container = container or build_container(settings)

    @app.exception_handler(ServiceError)
    async def service_error(_, exc):
        return JSONResponse(status_code=exc.status_code, content={"detail": exc.message})

    for module in (auth, users, items):                    # one module per area
        app.include_router(module.router)
    return app

The container= argument is what makes API tests fast: a test passes a container of mocks, so it needs no database, no model and no GPU.

5. Data

  • Every schema change is a new numbered file in backend/migrations/, applied at startup. Never edit one that has already run anywhere.
  • If users will ask "why did it do that?", store events (what happened, in order) and work out the current state from them. Don't store only the latest state.
  • When different users may see different parts of a record, write one function that builds each user's view, and test that the hidden fields never leave it.

6. Tests

KindFileSwapsProves
APItests/test_api.pyevery service is a mockroutes, sign-in checks, error codes
Enginetests/test_<engine>.pythe model is the fakeyour logic
Integrationtests/test_integration.pymodels are fakes; Postgres is realone whole user flow, start to finish

CI runs all of them, plus the frontend's type check, tests and build, and builds every Docker image. A failure blocks the deploy. Before calling any work done, run every suite the change touches.

7. Operations

  • Every container has GET /health (liveness: "the process is up"; it touches nothing else) and the backend has GET /ready (readiness: the database and other containers answer; return 503 if not).
  • Secrets come from environment variables, never from the repo. .env, *.tfvars and keys are in .gitignore.
  • Every new env var goes in four places together: app/config.py, docker-compose.yaml (with the same default), .env.example, and the deployment docs.

8. Adding a feature (the order to do it in)

  1. Migration, if the schema changes.
  2. DAO methods.
  3. Engine code, if there is real logic, with tests against the fake model.
  4. Service method: the rules, raising services/errors.py errors.
  5. Wire anything new in container.py.
  6. Controller route: one service call.
  7. frontend/src/api/client.ts and types.ts, then the page.
  8. Tests: API test, engine test, and extend the integration test if the flow changed.
  9. Update docs/STATUS.md, and docs/architecture.md if a box or arrow changed.

9. Write down the rules that cross files

Keep a table in CLAUDE.md of changes that must happen together, for example:

If you change……also update

Draw your map (task for the agent)

When the user asks for the architecture map, or after the first working version, write docs/architecture.md with:

  1. A Mermaid diagram of this project, in the shape below.
    • One subgraph per container.
    • Inside the backend, the layers top to bottom.
    • In each node: a short name, then the real code path.
    • Solid arrows for requests, dashed arrows (-.->) for startup wiring.
    • The pattern name in each node, in «guillemets».
    • Nodes this project adds beyond the reference get :::extra.
    • Leave out parts the project doesn't have.
    • Use the real folder names. If they differ from section 2, show the real ones and list the differences under the diagram.
  2. The directory tree of the repo, two levels deep, with a few words on each folder.
  3. A table: reference part → this project's part → what this project adds.
  4. One real service from this code, trimmed to about fifteen lines, with a comment on every call saying # adapter or # engine. Choose the service that touches the most parts. If a line is neither, say what it is. Do not invent or tidy: if an engine turns out to call a DAO or a client, or a service turns out to hold no order of its own, leave it visible and list it as a finding under the snippet. The point is to show whether this code keeps the split, not to show that it does.
