ML Capstone Platform

Annual Maintenance — getting the platform ready for the next cohort

Written at the end of the 2026 fall term, while the reasons were still fresh.

This is the list of things that have to happen between one cohort finishing and the next one starting, in the order they have to happen. It exists because most of these are invisible until they break in week one, when thirty people are waiting and there is no time to work out why a decision was made the way it was.

Each item says what to do, why, and how to know it worked. Where we deliberately chose not to do something, the reason is recorded — a deferred decision with no rationale gets rediscovered from scratch every year.

0. The one with a real deadline
Wildcard certificate expires2027-04-24 23:59 GMT
Covers*.ml-capstone.cs.byu.edu and the apex
Lives at/traefik/certs/ on rigel, declared in /traefik/dynamic/ml-capstone-wildcard.yaml
Issued2026-10-08 by CS IT (DigiCert), via ticket

This expires in the middle of spring, not during the summer window. Every student app URL goes to a browser certificate warning the day it lapses, and the admin UI with it. CS IT issues these on a ticket with lead time, so the request goes in February or March 2027 — do not let this one wait for the summer pass.

Verify after replacement:

echo | openssl s_client -connect ml-capstone.cs.byu.edu:443 \
  -servername anything.ml-capstone.cs.byu.edu 2>/dev/null \
  | openssl x509 -noout -subject -dates

Traefik's file provider watches that directory, so installing a new pair needs no restart. A single wildcard still matches one label only: www.<repo>.… is not covered and never will be.

The repository is private, and the docs publish themselves

ml-capstone-platform is private and stays private: its history carried student roster data, and keeping it private means the published site no longer depends on the source being public. Nothing about the student-facing URLs changed.

.github/workflows/docs.yml builds the book and pushes it into the public quinnsnell.github.io repository under ml-capstone-platform/, which Pages serves at the same addresses as before. Auth is an SSH deploy key with write access to that one repository, held here as the DOCS_DEPLOY_KEY secret.

Before each publish, scripts/check-no-roster-data.py scans the built site and fails the build if it looks like a roster reached it: more than two distinct email addresses in one file, or a delimited row with an address in it. It matches any domain, because over half the class used personal addresses.

What this means in practice:

  • Edit docs as always and push. The site updates by itself.
  • Never copy the roster into docs/. The check will stop it, but the ignore rules are the first line and this is only the backstop.
  • The GitHub ticket asking for the dangling commits to be purged is still open. That still matters even though the repository is private: the objects exist until GitHub collects them.

1. Summer: software updates

Do these in order. Each one can invalidate the testing you did on the previous one, which is the whole reason this is a sequence and not a list.

1.1 Coolify: 4.3.7 → current

We run 4.3.7. As of 2026-10-21 upstream had v4.4.7 out, plus a v4.3.24 on our own minor line. Take 4.3.24 first if you want to decouple "patch the line we know" from "move a minor version."

✅ Done early — rigel moved to 4.3.24 on 2026-10-21, not for this reason but because PHP2Shell forced it (see §1.2). Use scripts/upgrade-coolify.sh for any further bump: it pins the version, backs up Postgres first, and refuses to proceed on a partial dump.

The local #11449 patch is retired. It was reapplied after every upgrade from August 2026; upstream ships the fix as of 4.3.24. Confirmed two ways rather than assumed: the patch marker is in the stock image, and the call was retested with a genuinely team-scoped token (Quinn's Team, id 10) against the system-wide GitHub App — HTTP 201 where it used to be 404. scripts/repatch-coolify.sh is deleted.

Next Coolify bump is therefore 4.3.24 → whatever is current. 4.4.7 was out on 2026-10-21.

Also re-check after upgrading, because all three are things we measured against 4.3.7 and documented as fact:

  • ports_exposes is forced to 80 for dockercompose apps, making the UI's Port field inert. Our entire :PORT-in-the-domain convention rests on this.
  • The domain API contract (§3.1 below).
  • docker_compose_domains accepts a port and range-checks it.

1.5 Docker's address pool: check it after every update, and set it on any reinstall

Rigel's Docker networks must stay out of 10.x. If they don't, BYU campus and vpn.byu.edu users whose address falls inside a container network time out on every app, with no error anywhere (runbook §5a). This was found on 2026-10-21, and fixed by moving the pool to 172.20.0.0/14 and docker0 to 172.24.0.1/24.

Confirmed working from vpn.byu.edu on 2026-10-21, after the move: the clinic hostname and a Coolify-deployed app both load. That is the check that matters — applying the pool change proves nothing on its own, because the symptom only appears for a client whose address collides with a container network, and from the CS VPN everything looks fine either way.

Docker and Coolify upgrades keep the setting, but an OS reinstall or a new server doesn't. So after the summer updates, and after anything bigger:

ip -4 route | grep '^10\.0\.'      # must print nothing
jq '."default-address-pools", .bip' /etc/docker/daemon.json
  • If a reinstall is part of the summer: install Coolify with the pool given explicitly (runbook §5), set bip, and rebuild the Whisper container (§6b) so it binds to the new docker0 address.
  • Worth asking OIT once a year: whether BYU has started using any part of 172.16.0.0/12. If it ever does, the same failure comes back from the other side.

Rollback copies left on rigel by the move, with the dates they stop being useful. These outlived the move's own checklist, which is why they are recorded here rather than in a file that gets deleted:

Path on rigelKeep untilWhy
/etc/docker/daemon.json.pre-172indefinitely166 bytes, and the one-step undo for the pool change: cp it back and restart Docker rather than hand-editing JSON during an incident. The information is in §5a either way; what the file saves you is typing it correctly under pressure. No reason to ever delete it

One LiteLLM backup is deliberately not kept: config.yaml.bak-20261021-124800 still contains the castor autocomplete entry that was removed on 2026-10-19. Restoring it would put a dead backend back in the pool, so it was deleted rather than archived.

2. Summer: re-test the processes end to end

The scripts are idempotent and were all exercised this year, but they were exercised against this Canvas, this Coolify, and this GitHub. Re-run them in preview mode against a throwaway cohort before trusting them in week one.

./scripts/term-start.sh                      # previews all five phases
./scripts/smoke-test-cluster.sh              # 16 checks across the cluster
./scripts/verify-provisioning.sh             # read-only state check
python3 scripts/student-debug.py             # progress table

Specific things to re-verify:

  • Canvas API shape. canvas-roster.py joins the roster to the GitHub survey on canvas_user_id. It reads login_id and email off the student record and survey answers off a quiz. Any of that can move.
  • The survey itself. Quiz title Class Cluster Setup, three questions. find_quiz matches on title, so renaming it breaks the roster build.
  • FIM_HOSTS in smoke-test-cluster.sh defaults to pollux only. If castor rejoins the autocomplete pool, set it back to both or the check silently skips.
  • The class password. Rotate at term start: ./scripts/set-class-password.sh --generate. Students need it only for Coolify's delete confirmations.

Join on netid, never on names. 15 of 28 names differed between Canvas and the GitHub survey this year, and token overlap mismatches silently. Every roster join in this repo goes through canvas_user_id or an exact email, and any new one must too.

3. Decisions we deferred, with the reasoning

These are not bugs. They are places where we chose the cheaper option on purpose and wrote down why, so next year is a decision rather than an excavation.

3.1 The manual domain step in the lab

Students paste their domain into Coolify by hand, once per Application. We measured exactly why it cannot be automated today (terraform/probe/domain-patch-probe.sh reproduces all of it):

API callWorks?Condition
Create an app with docker_compose_domainsyesnone — and the port is preserved verbatim
Update one with docker_compose_domainsyesonly after docker_compose_raw is populated, which happens at the first deploy
Update supplying docker_compose_raw yourselfno"This field is not allowed." despite appearing in the API's own allowlist

The provider creates the Application, and at that instant docker_compose_raw is empty — so the domain cannot be attached yet. Automating it means apply → deploy → set domains → redeploy, with waits on two async deploys.

That is buildable and this is the window to build it, because it would also put the :PORT on the domain automatically and close the 502 failure class for every future student. It was not done mid-term because a half-working escape hatch in the repo thirty people learn from is worse than one honest manual step.

Lesson worth keeping in the lab either way: an allowlist is not a contract. docker_compose_raw is listed as updatable and is still rejected at request time. The only way to know what an API accepts is to call it.

3.2 The Terraform provider may be abandoned

bindtech-xyz/coolify is pinned at ~> 0.1.0 (lockfile: 0.1.2). Latest is 0.3.0, and its coolify_application schema is attribute-for-attribute identical to ours — so upgrading buys nothing for our use case and carries nonzero risk against live student state. That is why the pin is narrow.

The reason to look again is the project's health: 1 star, 0 open issues, 0 PRs, no commits since 2026-08-23. Nobody has even filed a request for docker_compose_domains. Options, in increasing cost:

  1. Stay pinned and automate around it with local-exec (§3.1).
  2. File the upstream issue. Costs nothing; expect nothing.
  3. Fork and add docker_compose_domains — the API supports it, so this is a provider-side change only.
  4. Drop the provider and drive Coolify's API directly from Terraform via restapi/local-exec. Loses clean state management for the main resources; probably not worth it for a teaching repo.

3.3 LiteLLM has no authentication — decided, and the answer is no

Decision taken 2026-10-21: we are not adding keys. Recorded here with the reasoning so it does not get re-litigated every year.

Anyone on the CS VPN can use classroom-chat, classroom-autocomplete, and classroom-transcribe with no key — curl with no Authorization header returns 200, and /ui/, /sso/key/generate and /model/info answer 200 too. The exposure is real: it is why CVE-2026-84377, scoped by its own advisory to "any authenticated proxy user", applied to us as effectively unauthenticated.

Why we are still not doing it. The cost lands entirely on thirty students configuring a secret in three different editors, and week one does not need that friction. What makes it tolerable rather than reckless:

  • the endpoint is VPN-only, so the population is the CS department, not the internet;
  • every api_key in the config is the sk-noauth placeholder, so there are no provider credentials to steal — the usual prize behind an LLM gateway is simply absent;
  • version currency is the real control, and we now pin it. Patching 1.92.0 → 1.92.2 closed that CVE in minutes.

The zero-friction version was investigated and does not work today. GenerateKeyRequest accepts a chosen key value, so in principle you could set an unpublished LITELLM_MASTER_KEY and mint a virtual key whose literal value is sk-noauth — every student's existing config would keep working untouched while the admin surface closed behind the master key. The blocker is that virtual keys need Postgres: LiteLLM has no DATABASE_URL, and /key/generate returns "DB not connected". Standing that up is a new database to run and back up.

Revisit if any of these change: the endpoint stops being VPN-only; real provider keys (OpenAI, Anthropic) enter the config, which changes the prize entirely; or LiteLLM gains a database for another reason, at which point the zero-friction path above becomes nearly free.

3.4 Whisper service details

Running: speaches (faster-whisper/CTranslate2) on rigel GPU 0, serving Systran/faster-whisper-large-v3, registered as classroom-transcribe. Installed and lifecycled by scripts/install-whisper-service.sh (--check / --rollback). See runbook §6b.

  • Model choice. large-v3-turbo is roughly 4× faster at close to the same English quality. Swap by downloading it and repointing the alias; the student-facing name does not change.
  • Unused endpoints. The image also serves TTS (/v1/audio/speech), /v1/realtime, and a Gradio UI. Harmless today because the container binds the docker bridge only, but decide whether to keep them reachable.
  • Not in term-start.sh. It is a persistent service rather than per-cohort provisioning, so it was left out. Add it to the summer rebuild checklist rather than term start.

3.5 Group-phase domains are still manual

Sixteen group-project domains were set by hand this year. If §3.1 gets built, this problem disappears for groups too. If not, a DB-write helper in the style of provision-teams.sh would do it — Coolify's applications.docker_compose_domains is plain JSON.

4. Changes this cohort forced, that the next one inherits clean

Context for why the docs look the way they do. None of these need action — they are already done, and the next cohort starts on the far side of them.

  • Service renaming. hello → frontend, time → backend, with the backend owning database access through a DAO and the frontend reaching it over HTTP. Mid-term migrations caused real confusion; a new cohort starts on the current names and never sees it.
  • HTTPS everywhere. Student apps serve real HTTPS as of 2026-10-08. The docs no longer tell anyone to use http://. Residual trap: curl without -L prints Found instead of following the redirect.
  • :PORT on the domain is now standard, not a remedy. It is harmless on a single-port service and prevents a 502-with-healthy-containers on a multi-port one. The template emits it; student-debug.py checks both directions.
  • student-debug.py scope. --all reads the roster CSV, which is now the group roster, so individual sandboxes show as "ignored non-roster teams." Fine during the group phase, surprising in week one. Point it at the individual roster, or add a flag.

5. One thing still uncommitted

hello-world-app has a local commit that is not pushed: the container port in the Coolify domain, split from the browse URL, plus the single-port comment on expose:. It was held back deliberately so students mid-migration were not reading a template that contradicted their instructions.

cd hello-world-app && git log --oneline -1 && git push origin main

Push it before the next cohort clones anything.

How to tell the whole thing actually works

In order, before any student touches it:

./scripts/smoke-test-cluster.sh                 # cluster: LLM, FIM, GPU hosts, Coolify
./scripts/install-whisper-service.sh --check    # on rigel: transcription chain
curl -s http://ml-capstone.cs.byu.edu:4000/v1/models   # all three aliases
./scripts/term-start.sh                         # preview provisioning, changes nothing

Then do the first-deploy lab yourself, start to finish, as a student would — with a fresh repo and a fresh token. Every failure mode documented in troubleshooting.md was found that way, and it is the only test that covers the instructions rather than the infrastructure.
